# 小程序人工验收清单

自动化测试覆盖 domain、API 客户端、存储与纯逻辑；UI 与真机行为需人工走查。
微信小程序的端到端自动化依赖开发者工具的 automator，阶段一不引入。

跑一遍前先确认：`cd miniprogram && npx vitest run` 全绿（文件数与用例数以实际
输出为准，不写死具体数字——会随迭代变化，写死了迟早对不上），`cd backend &&
.venv/bin/python -m pytest -q` 189 项全绿。这份清单只覆盖自动化测不到的部分，
不重复跑单测能验证的东西。

## 准备

1. `cd backend && .venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000`
2. `cd miniprogram && npm run build:weapp`
3. 微信开发者工具导入 `miniprogram/dist`，**详情 → 本地设置 → 勾选「不校验合法域名」**

## 无测试覆盖的高风险项

以下各条是历次代码审查中逐一指出的「diff 看不出对错、只能靠人工走查」的逻辑，
优先级高于下面的常规主链路走查。每条都写明了具体的操作步骤和期望结果，照做即可，
不要只是打开页面看一眼。

- [ ] **ArtCard 徽标（`count > 1` 才显示）**：收藏页里找一幅只抽到过 1 次的作品，
  确认卡片上没有「× 1」这种字样；再找一幅抽到过 2 次及以上的，确认显示「× 2」
  （或对应次数）。次数为 1 时完全不出现徽标，不是显示「× 1」。

- [ ] **art-detail 的三路分支（Task 11 核心业务规则，撤回 vs 下架的区分，
  无任何 CI 信号保护）**：
  - 用后端临时改一条作品记录的接口返回码，或直接改数据库让某个 `art_id`
    对应的记录返回 410，进详情页确认文案是「这幅作品已经下架，不再展示。」
    （`art-detail/index.tsx` 里的 `art__gone` 分支），而不是 toast。
  - 构造一次非 410 的失败（比如断网、或让接口返回 500），确认弹出的是
    toast「打不开这幅作品」，而不是白屏或崩溃。
  - **关键区分点**：找一条 `is_active=false` 但接口仍返回 200（附完整数据）的
    作品，确认它能正常渲染全部内容（图片、标题、作者年份、正文、来源），
    不能因为 `is_active` 为假就当成 410 处理。这是撤回（410，不再展示）与
    下架（200 + is_active=false，已收藏的仍可看）两种语义的分界，只看 diff
    看不出来，必须真的构造这两种响应各测一次。

- [ ] **collection 页的三种展示条件组合**：
  - `total_cards = 0`（从未抽到任何作品）：确认走空态文案，不是渲染空列表。
  - `total_cards > 0` 但 `unique_works` 与 `total_cards` 相等（每幅都只抽到过
    一次）：确认列表正常渲染，且没有一张卡片显示徽标。
  - `total_cards > unique_works`（有重复抽到的作品）：确认对应卡片显示正确
    的次数徽标，且顶部统计文案（如有）里的总数与去重数分别对应
    `total_cards` / `unique_works`，没有互换。

- [ ] **注销的四步顺序（后果最严重的一项）**：`settings/index.tsx` 里 `remove()`
  的顺序是 `await api.deleteAccount()` → `clearTokens()` → `clearDraft()` →
  `Taro.reLaunch(...)`。这个顺序不能变——一旦重构时把 `clearTokens()` 提前到
  `deleteAccount()` 之前，注销请求会丢失 `Authorization` 头，后端大概率按未登录
  处理（静默失败或 401），前端却依然清空本地状态跳回欢迎页，造成「本地已登出
  但服务端账号还在」且用户完全无感知的不一致，且没有任何自动化测试会因此变红。
  验收时：
  - 完整走一次真实注销：点「注销账号」→ 确认 → 观察网络面板确认
    `DELETE /api/v1/me` 请求带着 `Authorization` 头且返回成功 → 确认回到欢迎页
    → 重新登录同一账号，确认之前的夜记、收藏、设置都已清空（不是本地清空、
    服务端还在）。
  - 再触发一次注销，但在点「确认」前切到开发者工具的「无网络」，确认失败分支
    弹出「注销失败，请稍后再试」，且本地 token、草稿都还在（没有半途清掉一部分）；
    恢复网络后重试一次应能正常注销成功。

- [ ] **设置页 `patch()` 的乐观更新与回滚**：
  - 断网状态下切换「减少动态效果」开关：确认界面先立刻切换（乐观更新），
    请求失败后自动弹回原状态并 toast「保存失败」，不能停留在错误的开关状态上。
  - 连续快速修改两个不同设置项（比如先拖「计划入睡」时间，紧接着不等它保存完
    就切「减少动态效果」开关）：确认两次的乐观更新都各自正确显示，且两次
    请求都成功后界面最终状态是两处都生效，没有一次的结果被另一次覆盖回去。
    这类并发时序问题需要真实的（哪怕轻微的）网络延迟才会显现，模拟器本机
    请求几乎瞬时返回时不容易复现，建议开发者工具里加一点网络限速再测。

- [ ] **昵称 `onBlur` 的短路条件**（`settings/index.tsx` 里
  `if (!v || v === me.nickname) return`）：
  - 输入框留空或只输入空格后失焦：确认没有发出 `updateNickname` 请求
    （看网络面板），昵称保持原样。
  - 把昵称改成别的值后又手动改回原来的值再失焦：确认这次失焦也不发请求。
  - 反例对照：真的改成一个不同的合法昵称后失焦，确认这次确实发了请求且保存成功。

- [ ] **`Taro.showModal` 的确认/取消分支**：点「注销账号」弹出确认框后，
  显式点「取消」（不是点背景关闭），确认 `deleteAccount` 接口完全没有被调用
  （网络面板里不应出现这条请求），页面停留在设置页且数据不变。

- [ ] **story 页 `<Video>` + `<CoverView>` 的层级压制是否真机可点**：原生
  `<Video>` 组件层级高于普通 WXML 元素，代码里用 `<CoverView>` 承载「跳过」
  按钮来压住它，这个层级关系在开发者工具模拟器里未必如实反映真机效果。
  必须在**真机**（不是模拟器）上打开开场视频页，实际点击「跳过」按钮，确认
  能点中并跳转到今晚页，而不是点击穿透到视频本身或毫无反应。

- [ ] **`Taro.getStorageSync` 对不存在 key 的返回值**：`store/auth.ts` 里
  `getAccessToken` / `getRefreshToken` 依赖 `Taro.getStorageSync(key) || ''`
  这个写法成立的前提是「key 不存在时返回空字符串（或其它 falsy 值），而不是
  抛异常」。这是微信小程序官方文档的行为，但没有源码级实锤，且不同基础库版本
  理论上可能有差异。验收时清空开发者工具的本地存储（或用全新账号首次登录前
  的状态）直接打开小程序，确认不会在控制台看到未捕获异常导致白屏，登录态判断
  走的是「未登录」分支而不是报错崩溃。

- [ ] **断网首启后「退出再进入」能否触发重试并进入引导流程**：`app.tsx` 用
  `useDidShow`（而非 `useEffect`）调用 `routeAfterBootstrap()`，注释里写的
  设计意图是「小程序前台化都会重新走一次，用户退出再进这个自然动作就能重试，
  不需要杀进程冷启动」。这个「重新前台化即重试」的效果本身没有对应的自动化
  测试。验收步骤：断网状态下冷启动小程序（预期停留在某种失败/重试态，不崩溃）
  → 恢复网络 → 把小程序切到后台再切回前台（不要杀掉进程）→ 确认这次自动
  拉到配置并正常进入引导流程，不需要用户手动点「重试」按钮或重新冷启动。

## 主链路

- [ ] 首次打开：无任何登录弹窗，直接进欢迎页
- [ ] 三步引导可前进，最后一步进入开场视频
- [ ] 开场视频可播放；点「跳过」能进今晚页；视频取不到时不卡住
- [ ] 今晚页倒计时每秒走动，距离 10 分钟内变色（near 相位）
- [ ] 走完五步仪式，晚安页显示「明天早上来看看收藏」
- [ ] **当晚**去收藏页：没有新卡片（奖励不当晚揭晓）

## 揭晓窗口

- [ ] 把系统日期调到次日 05:59，重开小程序：无揭晓
- [ ] 调到次日 06:00，重开：自动进入奖励页，出现一幅作品
- [ ] 收藏页出现该作品，计数正确
- [ ] 点作品进详情，文章与来源完整显示

## 断点续做与草稿

- [ ] 走到「计划」步杀掉小程序再开：停在同一步，已填内容还在
- [ ] 把日期调到次日再开：草稿清空，回到第一步（**不得出现昨晚的内容**）

## 夜记编辑

- [ ] 次日 06:00 前打开夜记详情：有「修改」入口，改后保存成功
- [ ] 次日 06:00 后打开：无「修改」入口
